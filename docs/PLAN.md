# Terraria Agent 一天开发计划

本计划把一天的开发时间集中在可观看、可复现的真实游戏闭环。最低交付是观察、移动、砍树、拾取，以及正常制作工作台；主要挑战是收集资源、准备装备和场地并尝试克苏鲁之眼。长期推进到月亮领主，不承诺第一天通关。

制定日期为 2026 年 10 月 4 日，时区为 Asia/Shanghai。用户已选择最新版原版加轻量 C# 桥接，不再把 tModLoader 安装作为必需条件。当前使用自写、固定用途的 Host 与 Bridge，仅引入固定版本的 Harmony，不加载上游 Core、Injector、Vault、DebugTools 或可选游戏模组。公开 GitHub 远程已配置，实际查询成功且没有远程 refs，仓库可访问但尚未推送；此前的 TerrariaModder 固定源码静态审查保留为接入选型依据，见 SECURITY_REVIEW 与 DISK_BUDGET。下文的参数、步骤和时间保留为原始计划与准备预算，实际进展以 [VALIDATION.md](VALIDATION.md) 为准。

当前已实际创建并进入专用 Classic 人物与世界，自身观测与 12 秒连续录像播放验证通过。三次 A 尝试均等待人工许可超时，Agent 未执行动作，移动、停止和跳跃未通过；本轮死亡 4 次、人工接管 0 次，正常退出后专用新档已落盘。当前优先修复许可热键并复测 A，B、C、D 未实现，运行时仍为规则且未接模型。编译、22 项协议检查、21 文件备份与 16017 文件副本校验的准备记录继续保留；逐次实际结果见 [VALIDATION.md](VALIDATION.md)。

当前执行范围按 [今晚第一阶段计划](TONIGHT_PLAN.md)：约 3 小时，只推进 A，优先完成真实游戏闭环、安全停止与可复现交付。下文的一天安排保留为后续推进框架。

已安装原版 Terraria 1.4.5.8，路径为 `E:\SteamLibrary\steamapps\common\Terraria`，Steam build 为 24893155。Git 2.49.0、.NET SDK 9.0.201、.NET 8/9 运行时、.NET Framework 4.8 开发引用、FFmpeg 7.1.1 已存在。Windows 窗口查询可用；游戏窗口输入与游戏连续录屏尚未验证。C 盘约剩 124 GiB，E 盘约剩 768 GiB，第一天关键录像方案预计新增 5 至 15 GiB。

接入实现已改为自写、固定用途的 Host 与 Bridge，游戏内项目目标为 net48，使用固定官方 NuGet `Lib.Harmony 2.3.3`。不加载此前审查的第三方 Core、Injector、Vault、DebugTools 或可选模组，也不运行其部署脚本。本机原版方法签名和静态更新顺序已核对，见 [GAME_API.md](GAME_API.md)；实际补丁加载、图形/音频资源、云隔离和输入效果仍待进入游戏验证。tModLoader 稳定版 1.4.4 仅作为可能的备选；此前核实的 ModPlayer/ModSystem API 不适用于原版桥接。

最少准备步骤是：核对自有 Host、Bridge 与固定依赖；创建和校验隔离游戏副本；备份现有存档；待桌面交接后用独立路径启动；记录菜单版本和实际 SavePath；确认隔离后创建专用新人物与新世界。副本校验和备份已完成，实际启动与新档创建尚未开始。禁止运行将所有模组写入原游戏目录的 setup/deploy 流程。遇到登录、安装协议或确需用户处理的界面时，明确说明具体一步，其余工作继续推进。

启动前只读复制现有 Terraria 和已有 tModLoader 的 Players、Worlds、相关伴随文件，以及存在的 Steam Cloud remote 文件。对复制前后生成文件大小与 SHA-256 清单；游戏关闭时复制，存在同步活动则先等同步完成。备份不能被当成主挑战初始装备来源。当前已完成 21 个存档相关文件的备份；后续重新启动或备份时继续核对游戏关闭与同步状态。

原版桥接必须明确支持两个绝对存档根并在启动时核对实际 SavePath。原版 `-savedirectory` 与 Program/Main 路径初始化顺序已静态核实，自有 Host/Bridge 已实现根检查及云枚举、读写限制；这些保护尚未在真实启动、人物菜单和保存过程中验证，不能只凭启动命令或编译认定隔离成功。实际存档根、资源根或原有云存档影响任一未确认，都不得创建或加载人物、世界。`-tmlsavedirectory` 是 tModLoader 参数，不用于当前原版路线。任何情况下都不改动原有存档。

## 新档配置与挑战规则

主挑战已实际创建并进入单人新档：人物 `TA1`，Classic；世界 `The Annoyed Frontier`，Small、Classic、Corruption。种子输入框留空，由游戏随机生成，没有输入特殊种子。世界种子只用于人类验收记录和复现，不作为运行时 Agent 输入。

配置最终以创建界面和运行日志为准，记录人物难度、世界难度、尺寸、邪恶类型、种子、游戏版本、自有 Host/Bridge 与 Harmony 版本、启用组件、创建时间和决策模式。当前仅使用自有 Host/Bridge 与固定 Harmony；新档已落盘，退出后重进仍待验收。隔离目录的自有配置已开启 `AutoPause`，本次重新进入游戏后仍须确认实际生效，不能把配置写入当成暂停验证通过。

主挑战禁止刷物品、改血量或伤害、传送、跳时间、读取未探索地形或隐藏矿物。允许自身状态、背包、当前可见环境与此前合法观察到的信息。正常探索获得的装备、制作、平台和召唤条件都必须在主挑战内完成。

独立战斗测试档可准备装备、场地与召唤物，用于反复调试战斗；创建时记录所有准备方式，标记为 `combat_test`。其击杀、装备、死亡、人工协助与截图均不计入主挑战成绩，也不能把测试档物品转移到主挑战。

## 技术结构与信息边界

第一版用 C# 原版桥接与 C# .NET 本地控制器；进程内桥接匹配游戏的 net48，外部控制器使用已安装的现代 .NET。规则状态机是首个运行时决策层。Codex 在开发时帮助写代码、操作与检查；它不等于游戏运行时已连接模型。

模组在游戏线程内生成经过过滤的观测。字段只包含本地玩家位置、速度、生命、死亡/控制状态、背包，以及当前镜头内且有可见性证据的地形、树木、掉落物和敌人。镜头范围不是可见性的充分条件：黑暗、遮挡和地下未知格子必须过滤；信息不确定时不暴露。历史地图只更新已实际观察的格子，附首次和最近观察时间，未知保持未知。禁止序列化完整 `Main.tile`、全部 NPC、全世界物品或隐藏状态。模型也只能接收同一过滤结果。

通信初选 Windows 命名管道，限制当前本机用户连接，并显式拒绝远程客户端。仅设置 `CurrentUserOnly` 不足以保证本机范围，还要使用 Windows 的 `PIPE_REJECT_REMOTE_CLIENTS` 或经验证的等效实现；A 阶段检查这一限制。参见 [微软命名管道说明](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-createnamedpipea)。如果托管接口不能可靠做到这一点，改用严格绑定 `127.0.0.1` 并校验会话的通信，禁止绑定 `0.0.0.0` 或公网接口。游戏线程只读写有界快照队列；后台线程负责通信，不访问 Terraria 对象。原始存档与备份也不提供给决策层。

每条动作带协议版本、会话与世界标识、递增序号、参考观测号、有效期和控制参数。服务端用单调真实时间计算接收后的期限，并限制最大 TTL；陈旧观测、排队延迟、乱序、重复和错误会话都要拒绝。起点为最大 250 毫秒 TTL、控制器约 20 Hz 续期、输入按游戏更新执行；实际频率和停控延迟在 A 阶段测量。

本地控制器连续处理左右移动、跳跃、瞄准、工具使用、攻击和交互。进程内桥接要对齐原版 1.4.5.8 的实际方法、重载、更新顺序与框架事件，记录游戏线程中的控制应用和结果采样时机。不得直接使用 tModLoader 的 ModPlayer/ModSystem 类，也不原样复用 DebugTools 的宽权限 HTTP。完整更新不能当作每一渲染帧均发生，暂停时仍使用真实时间令旧动作过期。制作、放置和装备的实现另查正常游戏流程，不能直接改背包伪造成功。

决策层初始每 1 至 2 秒或技能结束后运行一次，选择任务、目标、撤退与挑战时机。规则模式没有外部模型调用。B 稳定之后保留 `IPlanner` 接口接已有模型；若使用另外付费的运行时 API，先询问费用与提供商，不假定 ChatGPT 订阅含 API 额度。不从零训练模型，也不搭建游戏运行时多 Agent 平台。

## 安全停止与人工接管

控制权状态采用 Manual、Agent 和 LatchedStop。默认 Manual；用户显式启用才进入 Agent。当前键位为 `Ctrl+Shift+Backspace` 紧急停止并交还人工控制，`Ctrl+Shift+Insert` 作单次人工许可后交给 Agent；键位与活动输入停止的实际结果以 [VALIDATION.md](VALIDATION.md) 为准。停止脚本同时终止续期，并向模组发停止消息；模组的 TTL 和断连处理独立生效。

过期、断连、死亡、进入菜单、切换世界、文本输入、失去有效会话或异常都清空 Agent 动作。释放 Agent 持续输入后允许人类正常操作，不覆盖人类当前输入。紧急停止与人工接管保持锁定；重连、复活或进入新世界不会自动夺回控制权，必须再次显式启用。

停止验收针对输入标志与角色结果分别检查。松开移动后角色可能因惯性继续一小段，不能要求瞬间速度为零；但输入必须在有效期加一个可执行更新内清空，并记录实际延迟。游戏完全暂停时不得保留可在恢复后重新生效的旧动作。

## 分阶段实施与验收

| 阶段 | 实施任务 | 真实游戏通过条件 | 失败时的范围控制 |
| --- | --- | --- | --- |
| A | 模组加载、合法位置观测、右移、停止、跳跃、断连释放、紧急停止 | 录像与日志对应位置变化、停控和跳跃；断开续期、过期、错误序号、暂停恢复、死亡/退世界与人工接管都不残留输入 | 只保留观察与左右/跳跃，修通信和控制权，不增加采集技能 |
| B | 发现可见树、接近、选斧、砍树、拾取、正常制作并放置工作台 | 可见树发生实际变化；实际背包木材增加；按游戏配方消耗材料且出现工作台物品；放置后物品减少且世界对应格子出现完整工作台 | 优先修当前失败环节，换合法可见目标；至少一次全程自动成功，争取连续三次 |
| C | 采石、正常制作与装备、照明、简单避险、搭战斗平台 | 背包、装备栏、照明和世界平台变化可核实，危险时会撤退，失败可恢复 | 做到实测可用的技能为止，复杂洞穴/长路径延期 |
| D 测试 | 独立准备档调试克苏鲁之眼 | 标记测试档的录像、Boss 血量变化、战斗结果、死亡与接管记录 | 根据失败原因改躲避、瞄准、补给或平台，不将测试成绩算入主挑战 |
| D 主挑战 | 主档正常获得装备、场地和召唤条件并尝试 Boss | 资源与召唤来源可追溯，保留尝试和结果录像；击杀才记录主挑战通过 | 接受未击杀结果；不跳夜、不刷召唤物、不降低规则门槛 |

A 开始前先录制 10 至 15 秒游戏短片，检查文件时长、帧解码以及播放器中的实际播放。仅有 FFmpeg 设备/编码器或成功生成文件都不算游戏录屏通过。若只有截图，验收材料明确写“截图”，不能称作连续录像。

B 必须从运行时合法观测发现树木，不能通过人工提前提供全图坐标。材料数量与工作台配方从当前安装版的合法游戏制作信息核对，不在尚未核实前硬编码成既成事实。工作台制作后，还要走近合法地点完成放置，并核对物品和世界变化。

## 技能的前置条件与失败恢复

每个技能返回 `success`、`failure` 或 `cancelled`，附任务号、开始/结束观测、原因、耗时、尝试次数和结果差异。建议统一原因包括 `target_unreachable`、`stuck`、`no_progress`、`insufficient_materials`、`station_missing`、`craft_failed`、`placement_blocked`、`unsafe`、`dead`、`expired` 和 `manual_takeover`。

| 技能 | 前置条件 | 成功依据 | 起始超时与恢复预算 |
| --- | --- | --- | --- |
| 移动到目标 | 目标在合法地图内，有局部可行路径，控制权有效 | 位置进入目标范围 | 15 秒；停下重观察，换站位最多 2 次 |
| 砍树或挖掘 | 目标合法可见、合适工具、距离可达 | 目标格子/树结构变化，持续进展可观察 | 30 秒总上限，连续 5 秒无进展则停；换站位/目标最多 2 次 |
| 拾取 | 已看到掉落物，有背包空间，路径安全 | 背包对应数量增加并能关联掉落物变化 | 15 秒；重观察后换路径最多 2 次，不能仅凭物品消失判成功 |
| 制作 | 配方已核实，材料足够，距离与工作站条件满足 | 背包材料和产物符合正常配方变化 | 5 秒；重读可制作信息和工作站，最多重试 1 次 |
| 放置 | 背包有物品，正常放置距离，支撑与空间有效 | 对应完整世界物体出现且物品正确消耗 | 5 秒；换合法位置最多 2 次 |
| 装备 | 正常背包槽存在物品、目标槽有效 | 装备栏实际变为目标物品 | 5 秒；重观察后重试 1 次 |
| 避险和战斗 | 已观察危险、已有合法装备/补给、可走区域 | 达到安全状态或明确战斗终局 | 按动作设置短期限，战斗有总上限；低血量撤退、死亡终止，无无限追逐 |

参数在实测后修订。卡住判断需要比较一段时间的位置、期望方向和目标进展，不能把短暂碰撞当作失败。达到预算后结束技能，由决策层重新观察、选其他目标或安全撤退；禁止原地无限重复。

## 一天的时间分配与停止扩展条件

按约 8 小时有效开发时间规划，依赖下载时间单独记录。时间块以进入实施阶段的相对时长计算，不代表已启动计时。

| 时间 | 重点 | 阶段结束时必须留下的结果 |
| --- | --- | --- |
| 0 至 0.5 小时 | 加载器版本与构建准备、存档备份与隔离、录屏短测 | 实际环境记录、备份清单、可播放短片或明确阻塞 |
| 0.5 至 2 小时 | A 的最小闭环与停止机制 | 在游戏中走、停、跳和断连释放的证据 |
| 2 至 4 小时 | B 的一条完整任务链 | 树、背包材料、制作和放置前后证据 |
| 4 至 5.5 小时 | C 的必要资源、装备和平台 | 每个已完成技能的实测结果和恢复情况 |
| 5.5 至 7 小时 | D 测试战斗，然后主挑战正常准备/尝试 | 两类存档独立的战斗结果和失败分析 |
| 7 至 8 小时 | 回归最小闭环、整理启动和交付 | 经过运行的一键启动入口、源码、日志、录像、当前限制和下一步 |

两小时仍未通过 A，就缩小输入和观测范围继续修 A；四小时仍未通过 B，就将剩余主要时间用于 B 和交付，不继续叠加 Boss 功能。最后至少留一小时整理与验证启动方式。真实游戏昼夜和召唤条件可能使 D 当天无法完成，照实记录，不靠跳时间解决。

## 验收证据与交付定义

每次运行生成独立 run id，并记录代码提交、游戏、自有 Host/Bridge 与 Harmony 版本、配置、`main_challenge` 或 `combat_test`、`rules` 或模型决策方式。日志包含观测引用、任务、技能、动作序号、结果、失败原因、死亡、人工接管、停控原因和延迟。录像时间与日志关联，保存关键前后背包、装备、世界变化和挑战结果。日志使用差分/压缩与保留限额，避免每帧保存完整环境快照使空间失控。

验收表分别填写：真实游戏成功、仅编译通过、仅单元/协议测试通过、失败与未实现。未开始运行的死亡和接管次数填“不适用”，不能用零次冒充成功运行。每次阶段通过后提交代码与摘要，只有真实通过的阶段才打验收标签。

最终交付包括完整源码、可运行且实测过的启动/停止/录屏脚本、精确版本与依赖说明、规则模式说明、原始本地日志、关键录像以及下一轮最优先修复的问题。公开仓库只存摘要和非敏感证据索引，游戏二进制和存档保持本地。
